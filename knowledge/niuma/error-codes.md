# NiuMa 错误码与响应契约

适用仓库：lboverfys/NiuMa
整理日期：2026-09-13

## 依据与适用边界

- 本地资料：`niuma-server/docs/architecture/error-code-conventions.md`，提交 `bab3e98d7e93c48a79796c83500746229a49b13e`。
- 原文：[查看固定提交资料](https://github.com/lboverfys/NiuMa/blob/bab3e98d7e93c48a79796c83500746229a49b13e/docs/architecture/error-code-conventions.md)。

本资料用于检查业务与代码是否一致。以目标提交对应的实际接口和较新的明确约定为准，不能仅凭旧文档的示例认定缺陷。

本文固定 NiuMa 的错误码归属、包结构、对外格式和号段分配。错误码是稳定接口契约，
新增常量前必须先确认语义归属和可用编号，已经对外发布的编号不得修改或复用。

## 1. 职责分层

- `niuma-common` 的 `ErrorCode` 定义统一契约，`SystemErrorCode` 只维护成功、参数、认证、授权、资源和未知系统异常等通用结果。
- `niuma-common` 的 `BusinessException` 统一承载可预期业务失败。
- `niuma-framework` 的全局异常处理器统一生成 `Result` 响应；技术基础设施错误由 framework 自己维护。
- 具体业务错误仍由业务事实域负责定义，但 Java 类型统一放在 `com.niuma.shared.error`，命名为 `XxxErrorCode`；类型名称对应其登记号段。

业务错误码不放进 `model`，也不集中到跨域 `BusinessErrorCode` 大枚举。这样既保持统一响应，
又避免所有业务域共同修改一个文件或让 `niuma-common` 依赖具体业务语义。

## 2. 编码规则

- 对外 `code` 固定为五位数字字符串，成功固定为 `00000`。
- 每个错误码在全项目唯一；枚举常量名称可以表达本域语义，但不能用名称代替对外编号。
- 每个错误码类型使用已登记号段，新类型不得自行占用空号段。
- 同一错误码类型按已有编号向后追加，不填补已经废弃或对外发布过的编号。
- 错误消息使用稳定中文，不返回堆栈、SQL、渠道密钥或其他敏感信息。
- HTTP 状态与业务码分别维护；调整 HTTP 状态不等于可以修改业务码，反之亦然。

## 3. 当前号段

| 范围 | 所有者 | 说明 |
| --- | --- | --- |
| `00000` | common | 成功 |
| `10001`-`10099` | common | 参数、认证、授权和通用资源错误 |
| `21001`-`21999` | identity | 身份与终端访问 |
| `22001`-`22999` | companion | 打手档案、接单、履约、作品、收益与提现骨架 |
| `23001`-`23999` | framework | 锁、幂等及其他技术支撑错误 |
| `24001`-`24999` | content | 媒体和内容处理 |
| `25001`-`25999` | communication | 会话和消息 |
| `26001`-`26999` | demand | 公开需求、候选、试音和成交前协助 |
| `27001`-`27999` | order | 报价、订单、预留和履约 |
| `28001`-`28999` | finance | 积分支付和充值 |
| `29001`-`29999` | support | 客服协助和售后工单 |
| `30001`-`30999` | refund | 退款单据和进度 |
| `31001`-`31999` | review | 订单评价 |
| `32001`-`32999` | notification | 站内通知、实时推送和订阅 |
| `33001`-`33999` | catalog | 目录配置；33001 标签重名，33002 标签版本冲突 |
| `50000` | common | 未识别系统异常 |

## 4. 自动校验

`ErrorCodeArchitectureTest` 在构建时扫描 common、framework 和 business 的全部生产错误码，
校验五位数字格式和全局唯一性；业务错误码还会校验统一包位置及错误码类型的号段归属。
新增错误码类型或号段时，必须同步更新本文和测试中的登记表。
