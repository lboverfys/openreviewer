# NiuMa 模块边界与接口契约

适用仓库：lboverfys/NiuMa

本项目的 Java/Spring、MyBatis 和 PostgreSQL 约束只适用于 NiuMa。结构规则用于核对新增依赖与数据所有权，不要求把其他仓库改造成相同目录。

## 业务事实归属与跨域调用

适用于 Controller、Service、Mapper 和跨域编排。Controller 做协议、校验和鉴权，通过 Service 接口进入业务；Service 实现在 service.impl，业务请求、响应、实体和查询投影在本域 model 下。复杂 SQL 位于 Mapper XML。Entity、Projection、Mapper 和实现类不直接成为外部调用方的业务契约。

跨域步骤由 shared.workflow 的接口和 impl 编排，原业务域保留表与事实的所有权。同库跨域原子事务可以成立，不能因为调用多个 Service 就误判为长事务；真正的 HTTP、文件和外部系统调用仍应离开数据库事务。

## Mapper 的读写边界

适用于跨表查询和数据修改。Mapper 写入或锁定的表归本域所有；确需跨域组合读取，按实际 statement、目标表和用途在现有 Mapper XML 架构检查中登记。只读例外不能延伸为跨域 UPDATE、DELETE、数据修改 CTE 或 FOR UPDATE。

表所有权由业务事实决定，不机械依赖历史前缀。例如退款表即使带 finance 前缀仍属于退款事实。报告需确认改动是否违反现有边界，不能把已登记的有界只读 JOIN 当作越界，也不能为了表名更整齐要求高风险改名。

## 五位错误码与浏览器数据类型

适用于 DTO/VO、异常处理和前端 API 封装。统一 Result 的成功 code 是字符串 00000；业务错误使用全局唯一的五位数字字符串，业务错误类型放在 com.niuma.shared.error，沿用所属类型的登记号段。已经对外发布的编号不改义、不复用。

HTTP 状态与业务码分别表达协议和业务结果。浏览器的业务 ID 保持十进制字符串，不能转换成可能失真的 Number；分页保持 PageResult 的字段含义。错误响应保留可排查标识并隐藏内部异常细节。旧示例中的 0、占位枚举和随意响应体不是兼容要求。

## 数据生命周期与迁移

适用于实体基类、迁移和审计。只有确实可修改、可软删除的普通实体才复用相应基类；资金流水、支付退款、审核轨迹和任务回执不因删除展示对象而抹去。金额与积分使用明确单位的整数，时间点保持 Instant 与 PostgreSQL TIMESTAMPTZ 的一致语义。

正式 schema 与系统基线通过 db/migration 前向迁移，演示数据与私有配置不进入正式基线。已执行迁移保持不变；不把当前迁移数量、成员分支或当时的环境状态当作代码契约。未确定业务可以保留未开放的契约，但不得开放返回伪成功的空实现。
