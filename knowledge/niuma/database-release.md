本资料用于检查业务与代码是否一致。以目标提交对应的实际接口和较新的明确约定为准，不能仅凭旧文档的示例认定缺陷。

## 查询与事务

- 使用 PostgreSQL，复杂 SQL 写在 Mapper XML；Mapper 只访问归属本域的表，跨域流程调用现有 Service/Workflow。
- 批量处理先收集 ID，用 IN/JOIN/批量接口读取，再在内存匹配。禁止循环内逐条 SQL、RPC 或 HTTP。
- 列表在数据库按权限和条件过滤后分页，指定稳定排序与上限；不把全表搬进应用后过滤。
- 查询选择实际列。条件应命中主键、唯一键或业务索引，避免给索引列套函数、运算或类型转换。
- ON CONFLICT 必须匹配实际唯一约束；若仅有部分唯一索引，冲突条件需包含对应谓词。
- 含积分、资源占用、版本更新的事务保持原子性；外部请求和耗时计算不放进事务。

## 已发布迁移不可变

- 正式迁移位于 niuma-bootstrap/src/main/resources/db/migration，联调种子位于 db/local。
- 任一共享环境已经执行的脚本视为发布，不能改名、改 SQL 或调整换行；使用更高版本前向修复。
- 新正式文件采用 V{时间戳}_{成员编号}__{小写描述}.sql；沿用项目约定的成员编号，不自行改历史编号。
- 禁止关闭校验掩盖 checksum/missing migration。clean 不用于共享库，repair 需要负责人明确决定。
- 不用业务单测通过代替真实 PostgreSQL 迁移检查；空库初始化、已有数据升级、并发边界各自验证。
- prod 不加载联调种子。当前共享环境发布走主分支 CI/CD，不能由代码审查工具自行执行远程迁移或重启业务。

## 审查结论需要可达证据

- 看见循环或空值访问时，要确认是否有实际 IO、数据规模、契约保障和真实调用路径。
- 测试夹具、源码回放、真实数据库测试、真实供应商调用是不同证据；不能互相冒充。
- 缺少关键上下文时降低结论确定性，说明需要查看的文件或规则，不编造需求、权限和服务响应。
