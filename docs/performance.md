## 流程整改的数据访问

单组评测概况访问 `evaluation_datasets`、`evaluation_cases`、`evaluation_observations`：先按评测集主键及仓库范围授权，再用一条 JOIN 聚合状态和已有 metrics，合计两条查询。每集最多 200 PR、400 组观察；复用 dataset_id 索引及 (case_id, variant) 唯一索引，查询次数 O(1)，不读取快照正文。

项目资料补充访问 `knowledge_library`、`knowledge_documents`、`knowledge_document_versions`：锁单行库版本，一次 IN 读取已有来源，两个批量 INSERT 写入缺失资料和版本。文档最多 128 份、启用正文最多 5 MiB；复用库主键、source 唯一键及文档/版本唯一键，查询次数 O(1)。本次补充 9 份、约 66 KiB，不覆盖已有编辑。知识列表在这一小规模集合内排序、分页，未增加无界查询或后台扫描任务。

检索开关与价格仍使用 `retrieval_settings` 单行 JSON；GPT 报价通过 `ai_settings`、`ai_provider_configs` 及现有配置审计保存。本轮没有新表或迁移，也没有在数据访问循环内增加查询、HTTP 或 RPC。

## 本轮新增查询与故障证据

新增访问 `static_analysis_reports`、`static_analysis_findings`、`review_reuse_entries`，并复用
任务、PR 版本、问题、仓库策略及评测三张表。静态线索按万至十万行设计，每页三条 SQL（授权、
报告身份、当前页），页内 AI 位置重合统计使用数据库子查询和 `(review_run_id, location_file,
location_start_line)` 索引；静态页使用 `(report_id, created_at, id)` 索引，查询次数 O(1)。

一次静态导入最多 500 条，批量 INSERT；解析在事务外。复用查询按主键哈希单次读取，正文上限
256 KiB；不随文件数量逐条查库。方案质量复用数据库聚合，并有界读取最多 400 条观察元数据，
不读取评测正文；限定单个最多 200 PR 的评测集，查询次数 O(1)。

`tests/integration/test_fault_recovery.py` 只在 CI 隔离 PostgreSQL 中启动真实子进程和回环 HTTP
桩。故障点位于 HTTP 返回之后、费用结算之前：终止子进程，确认预占保留、旧租约拒绝、替代
Worker 可领取及迟到结算重复调用只生效一次。全部断言通过后才生成 JSON 证据；Actions 产物
名称带完整提交 SHA，保留 30 天。它不测真实模型准确率、生产恢复耗时或供应商实际账单。

本页区分代码约束、CI 隔离验证和历史性能测量。它们不能互相替代。

## 当前查询设计

Worker 心跳按万至十万历史行考虑：在线摘要使用 `last_seen_at` 范围索引和窗口统计，正常一条
SQL 返回准确数量与最多三条预览；同一 SQL 在无在线节点时返回至多一条最近心跳，作为离线兜底。
历史页一条 SQL JOIN 任务与审查范围，复用游标封装和 `(started_at, worker_id)` 索引，每页十条。
上述查询次数为 O(1)，不随历史节点逐条访问数据库，也不把全部历史传给前端。七天保留与原有
有界清理继续生效，不通过前端隐藏替代数据保留策略。

| 场景 | 数据范围与查询边界 |
| --- | --- |
| 审查任务翻页 | 万至十万行；稳定游标、范围过滤、固定查询次数，正文按需读取 |
| 问题与事件 | 先核对任务范围，再按运行和排序键取当前页 |
| 评测收录 | 一次最多 30 条运行、六条批量查询，总快照最多 8 MiB |
| 评测报告 | 在数据库内聚合，不逐 PR 回查或读取全部正文 |
| 月度用量列表 | 月度汇总 JOIN 当前策略，一条查询，每页默认 10 条 |
| 请求账本分页 | month_id/仓库范围与 `(created_at, id)` 索引，一页一条查询 |
| 工作项与审批 | 范围、负责人、状态与稳定游标，单页固定查询次数 |
| 方案历史 | 只读取摘要，独立正文最大 2 MiB |
| 密钥轮换 | 最多四组有界读取、四组批量比较更新，加解密在事务外 |
| 模型计费与通道 | 每个真实 HTTP 请求固定数量 SQL；重试各自记账 |

查询次数 O(1) 指不随页面条数逐条增加数据库请求，不代表数据库计算量恒定。统计只在明确的
月份、时间范围或有界配置集合内进行。诊断聚合限制返回的仓库、错误类别与通道数量。

前端复用 128 项、8 MiB 的会话内缓存，最长保留五分钟，登录、退出和写入使其失效；
分页替换当前页，不无限累积历史记录。新运营页面复用同一套请求合并与分页机制。

## CI 的规模验证

- `tests/performance/management_scale.py`：一万与十万任务的游标翻页、查询次数、执行计划。
- `tests/performance/platform_scale.py`：十万请求账本的分页、跨页去重、固定查询次数和索引。
- `tests/integration/test_platform_postgres.py`：两个并发连接竞争月度预算与仓库执行名额。

这些脚本只接受隔离测试 PostgreSQL，造数按有界批次进行。它们不会连接业务库，不调用
真实模型；通过条件和日志属于对应数据规模的工程证据，不是公网 SLA 或模型吞吐承诺。
最终结果以目标提交的 GitHub Actions 为准。

2026-09-13 在提交 `87a526a` 的 [CI](https://github.com/lboverfys/openreviewer/actions/runs/34712384219)
中，后端 584 项通过、覆盖率 78.71%，前端 196 项通过。另有三项规模检查通过：
一万/十万任务分页与十万请求账本分页。后续修正的最终结果以对应提交流水线为准。

该次十万任务检查在总数缓存有效时，20 次服务层游标读取使用 40 条 SQL，P95 为 4.54 ms；
十万账本的两页读取使用两条 SQL，并命中 month_id/created_at/id 索引。这是 GitHub Actions
隔离数据库上的服务层调用，未包含 HTTP、登录、TLS 和真实模型时间。简历可优先引用
数据规模与查询次数，不能将该毫秒值写成公网接口延迟。

## 可保留的历史测量

2026-09-12 的独立容器回放使用 948 个文件、10,029 个代码块和 8,327 条已有向量。
API 与 PostgreSQL 各限制为 1 CPU / 512 MiB，客户端 0.5 CPU / 192 MiB。登录在计时前完成，
使用 HTTP 回环请求；不包括公网、TLS、Nginx 和真实模型延迟，向量/精排调用使用模拟客户端。

| 场景 | 条件 | 历史结果 |

| 关键词热缓存短回放 | 单并发，40 请求 | 中位 36 ms，P95 49 ms |

这是旧版本的受控记录，本轮未重复测量。冷加载约 2.9 秒的集中等待仍在历史记录中，不能只
引用热缓存数据。完整条件可在提交 `435b13a` 的
[历史回放说明](https://github.com/lboverfys/openreviewer/blob/435b13a/docs/architecture/frontend-and-concurrency.md) 查询。

给定样本中的候选近似程度，不能写成真实代码审查准确率。旧数据、原始测量环境与当前 CI
结果应分别陈述。
