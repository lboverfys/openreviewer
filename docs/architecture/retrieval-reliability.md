# 检索可靠性与工作台升级

本次补齐基础索引可用性、调用治理、增量源码读取、分组上下文、缓存维护与管理界面。保持现有 Python / PostgreSQL / React 架构，不增加常驻中间件。

## 使用方式

1. 在代码检索工作台选择仓库、PR 和提交，建立基础索引，无需向量 Key。
2. 基础索引就绪后，关键词和代码关系即可检索；向量暂停、失败或达到上限不会禁用它们。
3. 需要向量时，在服务端开放调用后显式点击补全；先检查新增数量上限，再受包含重试的请求额度限制。
4. 检索结果展示实际策略、降级原因、模型请求数、缓存、分组覆盖、源码与提交身份。

CLI 默认只建立基础索引；向量补全必须传 --include-vectors。评测默认只运行 bm25 与 lexical_relations，既可比较基础策略，也不会请求模型。

## 关键实现

- services/retrieval_indexing.py 负责阶段发布与增量补全；完成的基础快照不会因向量失败重置。
- services/retrieval_gateway.py 与 persistence/retrieval_runtime.py 负责共享租约、缓存二次检查、熔断和持久化请求额度。
- services/retrieval_context.py 按变更组组织查询与证据名额，批次通过 unit_keys 筛选上下文。
- GitHubCodeSourceLoader 先比较 Blob，再以最多20个文件的批次获取缺失正文。
- CodeIndexPanel 与检索工作区分开展示来源和结果；保留未评测状态，不生成虚假准确率。

迁移0049新增阶段字段、可为空的向量关联、增量源码缓存、精排缓存、供应商通道及请求额度表。代码向量和查询向量分别标记用途，已有8327条向量默认为代码缓存并保留。

## 验证与边界

发布前服务器完整回归524项通过，覆盖率76.67%；前端132项通过并构建成功。末次调整另行运行相关迁移、检索、缓存和前端验证，最终以当前提交的 CI 结果为准。浏览器验证使用独立的无模型夹具，390像素宽度无横向溢出；选用精排策略时，暂停环境实际返回关键词和关系结果，显示0次模型请求。

容量上限1000文件/20000块；后续性能升级已接入HNSW与精确回退，详见 [性能优化记录](retrieval-performance.md)。基础索引通过独立数据库任务入队，审查等待时释放自己的处理轮次；部署仍使用现有 Worker，尚未按硬件资源划分独立工作进程。

真实缺陷准确率、混合检索与精排增益仍需要用户开放模型后进行固定样本评测；已有录制回放和代理标注不会替代真实独立裁决。

## 运行约束

真实向量和精排保持关闭。构建、依赖与验证均在 niuma-2 或现有 GitHub Actions，Windows只编辑和同步项目文件。临时验证容器、目录和预览转发在部署验证后清除；正式数据卷、模型缓存、运维报告与备份保留。
