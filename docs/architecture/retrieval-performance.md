# 检索性能优化记录

基线代码为 9a70f1061ba37234147e2ced8fb4f56c2c2eca27。对照使用 niuma-2 上的独立PostgreSQL备份副本，不对正式服务压测，不请求向量或精排模型。

## 五项改动

1. 关联向量采用 UPDATE FROM，只更新实际匹配的空关联；没有新增向量不跑第二遍。10,029行真实关联表的重复关联验证中，实际更新0行，8,327条已有向量保持关联。
2. BM25的词权重和长度归一化贡献按版本预计算；查询只累加倒排贡献并用堆选Top-K。删除内存中不再参与计算的重复词频副本，按文件/符号定位变更范围。
3. 临时搜索不保存完整候选正文；旧临时记录14天过期并分批清理。审查证据的冻结、重试和保留逻辑不变。
4. 版本缓存增加LRU、128 MiB估算保留预算、最多4份快照和同版本冷加载合并；热缓存不会等待其他版本冷加载。单查询结果缓存最多128项，单项受查询长度和Top-K上限约束。
5. 向量检索按快照规模与覆盖比例选择HNSW或精确路径，HNSW候选严格按提交关联并在不足时回退。迁移0050增加候选关联覆盖索引和历史临时记录清理索引，不重建或重新生成向量。

## 对照数据

Python验证容器1 CPU，数据库容器1 CPU/512 MiB；同一服务器、同一数据副本，交替运行前后实现。

| BM25评分（索引已加载） | 106.78 ms | 11.65 ms | 10,029块，20个固定查询，3轮，关闭新查询缓存作公平比较 |
| BM25重复命中 | — | 0.003 ms | 仅内存结果缓存，不含HTTP、鉴权或数据库正文读取 |

| 精确回退 | 115.61 ms | 117.72 ms | 与原路径同量级；不把该差值宣称为优化收益 |
| 关键词检索服务调用（索引已加载） | 150.34 ms | 31.61 ms | 20个固定查询，包含数据库访问，不含HTTP和鉴权，模型暂停 |

BM25 P95由140.06 ms降至19.49 ms；评分一致，未出现排序变化。新词项结构逐对象核验约39.3 MB，原结构约82.8 MB；该数字不是进程RSS。生产采用较快的保守计量，加入5%余量和3 MiB查询缓存预留后，单份淘汰计量约45.0 MB，两份约90.1 MB，低于128 MiB预算。两个大快照交替访问只加载两次。

服务首次加载的单次对照为1886.26 ms与1850.40 ms，处于同一量级，不宣称冷加载明显提速。新实现连续20次手工搜索新增临时记录为0，候选与选择结果保持一致。

向量自适应路径P95为29.85 ms，原路径160.48 ms。相对精确Top-20，平均重合率99.75%，最差95%。EXPLAIN确认使用 ix_code_embeddings_hnsw 和 ix_code_index_chunks_index_embedding。这个结果只验证给定回放样本的候选接近程度及查询性能，不证明真实问答、审查或模型准确率。

## 访问规模与边界

单次检索读取 code_indexes、code_index_chunks、code_chunks、code_embeddings、code_relations；SQL次数为O(1)，候选正文最多150块，关系结果有上限。关联补全是一条集合更新，之后一条计数查询；只写缺失匹配，不对每块单独查询。版本加载使用有界游标，只有冷加载会读取整份词项元数据。

HNSW路径是近似检索；稀疏或小快照会直接精确检索，候选不足也会回退。OPENREVIEWER_VECTOR_SEARCH_MODE=exact 可保留完整精确语义。该开关与模型API暂停开关独立，性能验证期间后者始终关闭。

保留预算限制缓存持有的对象估算，不是Python进程的硬内存保证；正在处理的请求和冷加载还会临时持有对象。冷加载串行限制峰值，容器资源上限继续生效。性能数据是受控小样本对照，不作为生产并发容量承诺。

## 发布前验证

niuma-2独立环境中，后端539项测试全部通过（包含真实PostgreSQL回归），覆盖率76.92%，超过75%门槛；Ruff与94个生产文件的Mypy检查通过。前端132项测试、类型检查和生产构建通过。备份副本执行0050迁移及Alembic结构检查通过；全程没有调用真实Embedding或Reranker接口。
