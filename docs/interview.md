# 项目陈述与面试准备

## 一句话介绍

OpenReviewer 是面向团队 GitHub PR 的 AI 代码审查平台，围绕可恢复审查、跨文件证据、
人工批准、成本控制和评测追溯构建完整流程，首个接入对象是 Java / MyBatis 业务仓库 NiuMa。

## 简历表述草案

以下是功能与设计表述。投递前应确认自己能够解释对应代码，并把验证状态更新为实际记录。

- 基于 FastAPI、PostgreSQL 与 React 开发团队 AI 代码审查平台，结合 SKIP LOCKED、租约代次、
  批次检查点和 Outbox 处理异步审查与部分失败；通过预算预占、幂等结算、关联日志和人工批准
  保留任务及费用责任边界。可附目标 CI 实际通过的隔离故障、预算竞争与十万行验证记录。
- 面向 Java/MyBatis 建立版本化代码索引，组合关键词、向量与代码关系召回，以 RRF 和精排
  选择跨文件证据；将调参/验证分层，建立合成夹具的确定性检索回归与原因可追溯的引用核验。
  当前没有人工真实检索成绩，不填写质量提升数字。
- 实现不可变方案、Prompt 内容指纹与同提交候选试跑，建立单人日常核对和严格双人验收规则；
  指定评测可留存限量模型答案，关联调用账本、工作流快照及人工结论并归档复算。
  当前功能验证已实施，真实 PR 的独立人工评测待后续，不声称双人真实准确率。

篇幅有限时选三条，围绕求职岗位强调自己最熟悉的一条。规模测试、性能改善和准确率数字
只采用 [性能说明](performance.md) 与实际评测报告中的证据。

## 三分钟讲述顺序

1. **业务问题。** 团队 PR 需要审查，但直接调用模型缺少代码背景、恢复机制和责任边界。
2. **核心设计。** 每次审查固定代码提交，确定性规划后并发处理；结果和检查点先入库，
   由人工决定是否批准及发布。
3. **最难的问题。** 选一个并发预算、旧 Worker 写回、部分失败恢复或上下文漂移的问题，
   讲清触发条件、失败后果、实现和验证方式。
4. **效果证据。** 展示实际通过的 CI、查询规模验证或人工复核报告，说明测试边界。
5. **局限与取舍。** 单团队范围、固定 DAG、真实模型质量仍需积累样本等，按实际状态说明。

## 能深入展开的技术点

| 面试问题 | 代码入口 | 必须讲清楚的事实 |
| --- | --- | --- |
| 重复 Webhook 会不会重复执行 | `persistence/repositories.py`、`persistence/webhooks.py` | 接收幂等与执行重试是两回事，最终副作用还要对账 |
| 两个 Worker 抢任务怎么办 | `persistence/queue/scheduling.py`、`common.py` | 行锁、跳过已锁行、租约代次和过期恢复各负责什么 |
| AI 调用一半宕机怎么办 | `apps/worker/batches.py`、`persistence/queue/batches.py` | 成功批次复用、失败批次重试、截断检查点及不确定外部请求 |
| 高并发如何控制费用 | `persistence/usage.py`、`provider_channels.py` | 请求前预占、状态比较结算、未知用量、月末迟到与并发临界区 |
| 模型服务不可用怎么办 | `provider_channels.py`、`apps/worker/agent_pipeline.py` | 区分请求未获准与实际请求失败，熔断、半开探测、退避和已完成结果 |
| 改配置会不会影响处理中任务 | `services/review_profiles.py` | 配置捕获版本检查、不可变内容、任务绑定、凭据轮换与协议兼容 |
| RAG 如何支持跨文件审查 | `services/retrieval.py`、`persistence/retrieval.py` | 固定 SHA、符号/SQL 关系、候选融合、证据引用与降级记录 |
| 经验如何持续积累 | `services/review_learning.py`、`services/rag.py` | 人工来源、默认未启用、仓库范围、文档版本、冲突与恢复 |
| 如何证明不是只写了页面 | `tests/integration/test_platform_postgres.py`、`tests/performance/` | 真实数据库竞争、规模与索引证据、权限与状态回归 |

## 图片中的建议如何对应本项目

**混合检索与评测。** 已有混合召回、RRF、精排和检索评测。Recall@K 的分母是标注的相关项，
MRR 看首个相关项的倒数排名；RRF 是融合算法。必须说明标注单位、来源、调参与验收划分和
缓存条件，不能把相关代码命中当成缺陷找回。

**Agent 编排。** 当前使用固定 DAG 与持久化检查点。面试应解释为什么当前流程适合固定
节点，以及如何处理节点失败、并发与重试；项目没有使用 LangGraph，就不把它写入技术栈。
当前也不宣称实现了由模型自主决定工具调用顺序的 Agentic RAG。

**监控与治理。** Token、费用、请求明细、任务进度、错误和供应商通道都有可追溯记录。
讲“模型调用重试”时，应同时说明请求计费、未知用量和旧租约约束。

**记忆。** 本项目的任务检查点保存执行状态，缓存改善性能，版本知识保存人工规则与经验。
长期知识需要来源、范围与审核，不能从一次模型输出自动认定一条业务规则。

## 尚不能填写的结论

本轮可进一步展开三个问题：模型请求前怎样控制代码外发；如何将静态扫描线索与 AI 判断分别
呈现而不伪造“已验证漏洞”；如何把不可变方案与人工评测版本连接，并防止旧页面误用旧成绩。
精确输入复用可讲缓存身份、依赖失效、跨 SHA 引用重绑定和计量语义；应明确当前采用保守的
Agent 输入范围，并非全语言的最小依赖分析。

真实效果当前由用户确认为“待人工复核”。完成标签后，从评测报告页导出面试证据，结合对应
CI 的 Worker 故障恢复 JSON 展示。不要将故障桩、复用命中或录制输出描述为真实模型成绩。

- 没有真实复核数据支撑的“准确率达到 95%”“误报降低 40%”或“节省 80% 审查时间”。
- 将本地/隔离回放吞吐描述为公网生产容量，或省略缓存、硬件与模型模拟条件。
- 将一个团队的仓库权限称为已经完成多企业 SaaS 租户隔离。
- 将结构化审查快照称为供应商原始响应，将测试夹具称为真实人工金标。

准备面试时，选一个真实失败场景，带上问题、代码、约束、修复和验证记录。这比只背组件名称
更能体现你对项目的掌握。

## 五分钟演示与证据索引

本轮确认“先代码和部署、真实评测稍后”。演示时只使用已经归档的结果，不临场付费调用或
操作生产故障。没有真实样本的步骤直接展示功能约束与待验收项，不将合成数据导入生产冒充。

| 时间 | 展示顺序 | 可核查入口与边界 |
| --- | --- | --- |
| 0:00–0:40 | 固定 SHA、人工批准和发布边界 | `services/reviews.py`、`services/github_publisher.py`；真实 PR 案例待补 |
| 0:40–1:40 | Java/MyBatis 跨文件关系与失败查询 | `tests/fixtures/retrieval_regression/`、检索回归 JSON；明确合成样本 |

| 2:30–3:30 | Prompt 候选、同 SHA 独立运行与双人规则 | 候选页面及 `test_profile_candidates.py`、`test_dual_evaluation.py`；不展示虚构质量改善 |
| 3:30–4:20 | 费用分母、恢复和日志关联 | `test_fault_recovery.py`、`test_platform_postgres.py`、`query-plans-<SHA>`，按最终 CI 实际结果说明 |
| 4:20–5:00 | 验证取舍和未完成项 | 实施记录、告警 firing/resolved；外部渠道与三类真实报告仍待后续 |

工程证据包包括本地覆盖率、合成检索正/负向报告、隔离告警报告和目标 SHA 的 CI 产物。
关键代码入口：`persistence/evaluation_reports.py` 的严格筛选、`services/review_profiles.py` 的
不可变候选、`apps/maintenance/export_workflow_evidence.py` 的哈希归档与复算、
`persistence/usage_statistics.py` / `review_insights.py` 的指标分母、`domain/logging.py` 的安全日志。

后续真实评测最小补件：授权仓库/PR 范围、总费用上限、第二位独立复核者；固定数据划分、
标签版本、基线/候选假设与相同 SHA。保留失败、分歧、未知费用；达到原有 20 组参考配对及
样本构成要求才讨论方案验收。需要实际检出与误报/漏报两个真实案例；当前隔离恢复案例只证明
工程行为。没有结果改善时也如实给出对照和选择，不反复调参直到出现期望数字。
