# 检索与知识契约

目标是在固定 PR 提交下，为审查提供可追溯的关联代码与团队规则。
所有检索结果都要能回答：来自哪个提交、哪个文件、什么符号、为什么被选中。

模型连接、价格和调用开关统一放在“模型配置 → 代码上下文”；“审查依据 → 代码检索”负责索引、搜索和来源核对。
`external_calls_enabled` 未保存时兼容旧部署默认值；保存后以页面值为准。关闭只暂停向量与精排 HTTP，关键词/关系检索和 GPT 审查继续独立工作。
固定方案的下一次检索操作读取当前开关，模型及索引参数继续使用原方案。

知识文档的 `repository_scope` 在创建、编辑和读取接口中显式表达；空值表示通用规则。项目资料补充接口按现有知识库版本锁批量添加缺失文档，不覆盖已有版本或人工修改。
检索价格按 JSON 模式序列化，非空 Decimal 单价不会再使配置指纹计算失败。

## 索引与召回

Java / MyBatis 文件按语法结构解析，保存方法、SQL、符号引用和源代码哈希。索引以提交和
配置版本区分，源码、解析结果与向量按内容寻址复用；源码按 Blob 增量读取。

| 路径 | 作用 |
| --- | --- |
| BM25 | 基于符号、词项和倒排列表查找相关片段 |
| 向量 | 使用百炼生成的向量做语义近邻检索 |
| 静态关系 | 从变更符号、方法调用和 Mapper/SQL 关系补充跨文件证据 |
| RRF | 用各路名次融合候选，常数 k=60，同路重复结果只计一次 |
| 精排 | 对融合后的有界候选重新排序 |

RRF 是排序融合算法。Recall@K、MRR 等才是用标注数据衡量检索效果的指标。
不同召回路径的原始分数不能直接解释成准确率。

基础索引与向量补全分阶段发布。外部模型暂停时仍可使用关键词与关系检索；补全向量需要
显式请求。`OPENREVIEWER_RETRIEVAL_API_DISABLED` 仅作为尚未保存页面开关时的兼容默认值。
保存后 API 与 Worker 使用页面控制值；审查方案不能把过期的开关值带回新检索操作。

## 边界与性能

- 单次索引最多 1,000 个源文件、20,000 个代码块；单文件 256 KiB、单块 6,000 字符。
- 向量 HTTP 每批最多 20 段。正文只按有界候选 ID 一次 JOIN 取回，最多 150 块。
- 关系召回最多两跳，使用有界 JOIN；融合最多 30 个候选，默认最终上下文 8 条、总正文 24 KiB。
- 审查按变更组构造查询，各组轮流取得上下文配额。证据携带 unit_keys，模型分批只接收适用组。
- BM25 预计算词项贡献，访问命中的倒排列表并用堆选 Top-K。索引缓存最多四份、估算保留预算
  128 MiB；同版本冷加载合并，查询缓存有数量上限。
- 向量查询支持精确与自适应 HNSW 路径。小快照、稀疏关联或近似候选不足时保留精确回退；
  `OPENREVIEWER_VECTOR_SEARCH_MODE=exact` 可要求精确路径。

关闭、额度耗尽、通道占用或供应商失败时，普通检索可返回基础结果，并记录实际策略和降级
原因。对照评测发生策略降级时拒绝保存为成功对比。检索条数或 covered_units 只描述获得
上下文的范围，不等同于找回缺陷的比例。

## 证据与重试

ContextEvidence 保存 reference_id、索引、提交 SHA、文件 Blob、符号、行号、原文及哈希。
模型只能引用已有 reference_id。平台验证引用与内容一致性，行内评论的位置仍属于 PR diff。

首次上下文按运行、计划指纹和 Agent 唯一保存。重试复用该快照，避免一半批次使用旧检索
依据、另一半使用新依据。模型调用、缓存命中、路径得分、名次和警告保存在检索轨迹中。

当前流程是确定性的混合检索加固定 Agent 编排，没有宣称模型可自主循环选择工具和追加
任意查询。引入这种能力时，需要额外约束轮数、工具权限、费用和停止条件。

## 知识版本与人工经验

知识库最多 128 份 Markdown 文档，支持编辑、启停、归档和恢复历史版本。写入同时检查库
版本和文档版本，旧页面不能覆盖新内容。版本正文不可变，列表和历史分页不加载全部正文。

通用知识的 repository_scope 为空；从人工工作项整理的经验带有具体仓库范围。Worker 和
方案捕获都会过滤该范围。文档改名不会清除范围，其他仓库不能通过同名来源取得这份经验。
经验草稿默认未启用；记录来源工作项及版本，后续工作项变更不自动覆盖知识。

绑定不可变方案的任务使用方案内知识内容和检索参数；新增或启用知识后，需要保存并启用
新方案才影响后续任务。未绑定方案的任务继续使用原有知识库机制。

## 数据与验证

核心表为 code_indexes、code_chunks、code_index_chunks、code_embeddings、code_relations、
retrieval_traces、retrieval_evaluations，以及知识库的 library/document/version 表。
单次检索的查询次数为 O(1)，索引批量构建按批次数增长；冷加载使用 500 行游标批次。

检索评测使用固定查询集，记录数据来源、提交、索引、模型、策略与缓存条件。方法或 SQL
语句级相关性标注用于 Recall@K 和 MRR，不能代替真实缺陷标注。详见[评测口径](evaluation.md)
与[性能说明](../performance.md)。

审查中的向量与精排请求进入新任务账本，可配置每百万 Token 价格。独立索引、手工检索和
连接测试仍以供应商控制台核对费用，不混入审查任务成本。
